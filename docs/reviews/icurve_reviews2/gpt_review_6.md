## 1. [P1，内部 Terminator] 同一缓存会混用两种参数重建规则

**位置：**

`ICurveEvaluation.EvaluateTerminator`  
`EvaluationSampleStore.TryFindExact`、`TryInsert`

### 本次修复使原有的键缺口成为实际错误命中路径

当前已经正确地让 Terminator 使用与自身求解要求相容的质量门槛，并存入实际数值误差估计。因此，同规则下的重复查询终于能够命中缓存。

但缓存键仍然没有包含：

```text
TerminatorParameterRule
或对应的 ParameterizationRevision / 重建上下文
```

`EvaluateTerminator` 虽然先按本次规则重新计算 `terminatorParameter` 和 anchor，随后查缓存时却只传入：

```text
t、QueryKind、Side、Order、质量门槛
```

命中后直接返回旧样本，没有验证它是否使用同一个端点参数重建规则。

**缺少规则标识是既有结构问题；本次让 Terminator 样本可以正常精确命中后，它变成了可触发的错误成功路径。**

### 一个完全线性的反例，不涉及 Newton 困难

使用：

```text
Support0：平面 z=0
Support1：单位圆柱 x²+y²=1
TermUse：First，选择平面

原 chart：
P0 = (1,0,0)
P1 = (0,1,0)

base_parameter = 0
base_scale     = 1

终结点 E = (-1,0,0)
branch B = P1 = (0,1,0)
```

原 chart 末端参数为：

\[
t_B=\sqrt2.
\]

查询：

\[
t=t_B+0.5.
\]

当前两种规则的公式不同，得到：

| 规则 | 重建的 \(t_T\) | 同一查询 \(t\) 下的正确位置 |
|---|---:|---|
| `ExtensionRatio` | \(2\sqrt2\) | \((-0.3535533906,\;0.6464466094,\;0)\) |
| `TangentMatching` | \(\sqrt2+1\) | \((-0.5,\;0.5,\;0)\) |

这些数值直接来自当前 `TryResolveTerminatorParameter` 的两条公式。因为所选面是 `z=0`，区间解就是相应的弦点 \(Q(t)\)，不需要复杂曲面校正。

执行序列为：

```text
1. 用 ExtensionRatio 求值，写入共享 EvaluationSampleStore。
2. 保留同一个 store。
3. 同一 t、同一阶数，改用 TangentMatching 求值。
```

按当前命中条件与平面制造解复算，第二次调用会返回 `ExtensionRatio` 的点，而不是 `TangentMatching` 的点：

```text
返回位置：
(-0.35355339059327373, 0.6464466094067263, 0)

本次规则下的正确位置：
(-0.5000000000000001, 0.4999999999999999, 0)

位置误差：
0.20710678118654774

本次目标弦平面残差：
约 0.2071067811865477

当前复用门槛：
约 1.4142135623730952e-7
```

缓存仍返回 `Success / Exact`。反过来先预热 `TangentMatching`、再请求 `ExtensionRatio`，同样错误。

**这不是缓存复用了一个精度稍差的近似点，而是复用了另一种参数定义下的答案。**

### 修复建议

有两种合理方案。

**最小方案：让一个缓存实例绑定不可变的参数重建上下文。** 切换规则时，清空不相容样本或明确拒绝不相容的缓存上下文，不能继续精确复用。

**通用方案：将规则及其版本纳入样本语义键。** 不仅 `TryFindExact` 要检查，重复键合并、质量升级、近邻查找和后续 L3 传递也必须使用同一上下文，避免在插入阶段先把两种定义合并。

参数重建规则不是 I1/P2 这种“同一问题的求解表示”，不能因为求解计划允许跨计划复用，就认为规则也可以忽略。规格 §13.2 已包含 `ParameterizationRevision`，§13.4 也要求精确命中的语义满足本次请求。

应保留现有“同规则第二次精确命中”的正向测试，再增加两种方向的规则切换测试。

**范围限定：** 当前公开默认路径仍使用 `Unresolved` 并受 GATE-T 限制；此项是显式实验规则入口的确定错误成功，不应扩大为公开 PK 路径已开放该行为。

## 2. [P2，Spun 残留] 新误差项仍会把同一条轴的不同参考点判成不同正则性

**位置：**

`SweptSpunImplicit.SpunConstraints`

本次将原来的完整距离阈值改为：

var tolC =
    1e-12 * Math.Max(1.0, radNormC)
    + 2e-16 * Math.Abs(zc);

X 点采用相同形式。这个修改确实让上轮 `z=10¹³、半径=1` 的用例通过，但**阈值仍显式依赖轴向坐标**。

### 原反例改善了，但机制没有完全解除

保持单位 Z 轴和半径 1，将轴向位置设为一个可精确表示的值：

\[
L=2^{53}=9007199254740992.
\]

输入：

```text
axis              = (0,0,1)
point             = (0,1,L)
profilePoint      = (1,0,L)
profileDerivative = (0,0,1)
```

比较两个表示**同一条轴线**的轴点：

| 轴参考点 | 两个径向长度 | 当前阈值 | 当前结果 |
|---|---:|---:|---|
| `P=(0,0,0)` | 都为 1 | 约 **1.8014398509491985** | **`Singular`** |
| `P=(0,0,L)` | 都为 1 | `1e-12` | `Success` |

角度恢复函数相应地从 false 变成可以返回 \(\pi/2\)。

这不是要求忽略真正的浮点投影误差。**本例的轴是精确的 `(0,0,1)`，径向投影各步都能精确完成，巨大的 Z 不会污染 X、Y；两个约束的正确残差均为零。** 当前是通用的 `2e-16 * |z|` 项，把一个正则点当成了轴上退化点。

本轮复算也确认，上轮 `L=10¹³` 用例现在两种参考点都成功。因此应记为“原具体输入修好，参考点不变性仍有残留”，而不是说修改完全无效。

### 修复建议

不要继续通过减小 `2e-16` 来移动失效边界。

需要区分：

```text
真实径向退化
与
当前计算无法可靠区分径向量
```

前者可以返回 `Singular`；后者应由具体运算的误差估计支持，并采用适当的数值失败诊断或更稳定的局部表示。

对于误差估计，应考虑投影分量的实际运算结构，不能只用轴向距离给所有方向施加同一个地板。也可以在保持同一轴线的前提下，使用靠近当前 profile 的局部轴参考点进行计算；轴向高度差优先直接计算 \(\hat A\cdot(x-C)\)，避免两个大投影再相减。

新增回归应同时保留 `10¹³` 成功控制，并覆盖上述精确 Z 轴构造。当前测试只覆盖了前者。

## 3. [P2，验证脚本] 圆锥探针已有真实断言，但断言仍不是“异常输入必拒绝”

**位置：** `scripts/ConeAxisProbe.cs` → `AssertNear` 及接收验证循环。

### 3.1 `AssertNear` 对 NaN 会直接通过

当前辅助函数为：

```csharp
var diff = Math.Abs(expected - actual);
if (diff > tol)
    throw ...;
```

因此：

```csharp
AssertNear(1.0, double.NaN, 1e-14, "axis");
```

不会抛错，因为 `NaN > tol` 为 false。预期值为 NaN 时也一样。

这里确认的是**探针判定器的边界漏洞**，不是说已归档的这次 PK 数据包含 NaN。归档数值都是有限值，不能据此否定这次观察。

建议检查 expected、actual、tol 及计算后的 diff 均有限，并要求 tol 非负。负向测试直接调用这个辅助函数，避免重新复制一份判断表达式。

### 3.2 接收后还应确认确实检查到了目标圆锥

Direction B、Direction D 中，数值断言位于遍历 received parts/faces 的循环内。若没有遍历到圆锥面，这些断言就不执行，但脚本最终仍能打印：

```text
ALL ASSERTIONS COMPLETED SUCCESSFULLY
```

当前应增加每个方向的有效样本计数，并对该单圆锥夹具要求检查到预期数量的圆锥面。接收状态成功不应单独等同于目标几何验证成功。
